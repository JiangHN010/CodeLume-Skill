# 复杂模块章节契约

只有模块内部设计能够实质性帮助理解项目时，才使用完整模块章节。模块至少包含一种
非显然机制才符合条件：状态或生命周期转换、顺序或并发、多方边界、重要数据转换、
算法或策略选择，或者有意设计的故障隔离。

简单包装器、清单、注册表、值类型或单向适配器，使用总览或精简模块地图说明即可；
除非它们内部也包含上述机制。

## 面向读者的章节

讲清：

1. 模块吸收了什么架构压力，以及这项职责为什么需要独立；
2. 它的公共边界、拥有的状态或不变量，以及委托出去的工作；
3. 一个具体输入或状态变化怎样经过重要决策；
4. 项目避开了哪些替代方案，选择当前方案产生了什么后果；
5. 模块的代价、失败边界，以及什么条件下根本不需要这个模块。

只有正文会遮蔽机制时，才读取
[visual-learning-assets.md](visual-learning-assets.md)。模块不会因为存在就自动获得图表。

## 完成条件

本节必须教会读者模块为什么形成当前形状，以及其机制怎样运行。如果只罗列导出、
依赖或职责，就把它缩减为一个带源码链接的段落。
