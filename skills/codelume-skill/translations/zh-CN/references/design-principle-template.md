# 设计原则章节契约

对每项真正塑造项目的原则单独使用本契约。证据或可讲深度不足时，减少原则数量。

## 内部因果简表

写面向读者的正文前，在内部填满每个槽位：

- **设计压力：** 已验证的约束或反复出现的问题。
- **简单方案：** 一个有能力的开发者最初可能选择的可行实现。
- **具体失败：** 一个输入、事件、规模、变更或恢复场景，使简单方案变得错误、
  昂贵、僵化或难以观察。
- **推导路径：** 为什么这项失败会指向项目采用的边界或机制，而不仅是排除简单方案。
- **源码机制：** 初始状态、决策、调用、状态或数据变化和可观察结果，并链接准确符号。
- **收益：** 实现了什么行为，或降低了什么风险。
- **代价：** 新增了哪些复杂度、延迟、状态、耦合或运维负担。
- **边界：** 在什么条件下简单方案反而更合适。

无法用证据支撑全部槽位时，不加入这项原则。根据当前源码反推的历史动机必须标为
`[INFERRED]`。

## 面向读者的教学正文

把简表转化为连贯教学正文：

1. 建立设计压力和看似可行的简单方案。
2. 走完具体失败过程，让后果可见。
3. 推导项目的回应，解释每一步设计为什么自然产生。
4. 沿真实源码和一个具体状态或输入追踪这套回应。
5. 对比前后行为，再讲清代价和边界。

如果有助于读者巩固这项原则，可以用一个短段落收尾，只说明它解决的更普遍问题、
设计持续有用所需的条件，以及何时简单方案更合适。把这段内容留在当前原则内部，
写完这三点就结束。

## 完成条件

读者无需相信模式名称或优点总结，就能回答“为什么需要这种形状”“它运行时在源码
中发生什么”以及“什么条件下它值得采用”。任何一个答案缺失时，继续深入或删除这项
原则。
