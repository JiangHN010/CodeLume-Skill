# 源码分析操作手册

当仓库较为陌生、包含多个模块，或者运行时装配隐藏在框架和配置中时，使用本手册。

## 1. 确认代码快照

记录足够的信息，让教科书可以被复核：

- 仓库根目录和相关子项目；
- 当前提交、分支；无法获得 Git 信息时记录快照日期；
- 工作区是否存在未提交修改，但不要改动这些修改；
- 仓库级说明和文档约定；
- 使用的语言、构建系统和可执行入口。

优先使用 `rg --files` 和目标明确的搜索，避免无差别递归读取。文件名和目录名只能作为线索，必须由代码、配置或测试确认它们的职责。

## 2. 建立系统地图

在追踪单个函数前，先建立一张精简的工作地图：

| 问题 | 应检查的证据 |
| --- | --- |
| 什么能够启动系统行为？ | 路由、main 方法、命令、任务、消费者、导出接口 |
| 模块边界在哪里？ | 构建清单、导入关系、构建模块、包结构 |
| 具体实现如何被选择？ | 构造函数、依赖注入模块、注册表、注解、配置 |
| 持久状态存放在哪里？ | Repository、数据库迁移、Schema、文件系统适配器 |
| 哪些调用会离开当前进程？ | HTTP 客户端、SDK、消息队列、子进程、工具调用 |
| 什么在约束系统行为？ | 测试、参数校验、功能开关、安全规则、超时设置 |

不能只根据包名判断架构职责。教科书中的每个核心模块，都至少要确认一个真实调用者和一项已经实现的职责。

## 3. 追踪一条纵向流程

选择一个用户可见或外部可观察的场景。探索时使用下表记录调用链：

| 步骤 | 真实符号 | 输入或状态 | 执行工作 | 输出或副作用 | 证据状态 |
| --- | --- | --- | --- | --- | --- |

从两个方向搜索：从入口向下追踪被调用者，同时反向搜索关键实现的调用者。框架经常会打断源码中直观可见的调用链；此时应通过注册代码、注解、生成的元数据或测试补上这段关系。如果仅凭当前仓库无法证明运行时会选择哪个实现，把这个连接标记为合理推断。

遇到异步处理时，根据项目实际情况区分以下时刻：

1. 发起线程接收任务或把任务放入队列；
2. 本地回调或 Future 表示任务已经交接；
3. 外部系统确认已经收到请求或消息；
4. 消费者或工作线程执行真正的业务逻辑；
5. 持久状态或最终响应记录业务已经完成。

这些时刻不能被合并描述为一个笼统的“成功”。

## 4. 检查数据和状态

对于每个重要对象，找出它在何处创建、校验、转换、存储、复制和释放，并说明数据所有权和一致性边界。重点检查：

- 请求和响应模型；
- 领域实体和值对象；
- 持久化记录和数据库迁移；
- 缓存及其失效机制；
- 事务开始和提交位置；
- 用于关联重试或事件的标识符；
- 可变共享状态、锁和线程本地上下文。

## 5. 追踪失败行为

找到负责处理非法输入、数据缺失、外部超时、重复任务、重试、回滚、资源清理和用户可见错误映射的代码。只描述有源码或测试支撑的路径。项目依赖某个库，只能说明该能力可能可用，不能证明项目已经配置并实际使用了它。

## 6. 核验结论

选择能够推翻错误结论的检查方式，例如聚焦的单元测试或集成测试、相关模块编译、本地示例命令，或者查看生成的路由元数据。记录跳过了哪些检查以及原因。

写文档前，对每条重要结论提出以下问题：

- 哪个文件和符号能够证明它？
- 它描述的是源码结构、配置意图、测试行为，还是实际观察到的运行时行为？
- 依赖注入、配置、并发或外部服务是否可能改变结果？
- 对于当前代码快照，这条结论仍然成立吗？

不能得到可靠回答的结论，应改为合理推断、设计建议、尚未确认，或者从文档中删除。

## 7. 把证据转化为设计教学

写成连贯的技术章节，而不是审计报告或工作表：

1. 从问题、约束和一句架构主线开始。
2. 使用正文配合整体图讲解主要边界。说明每个边界为什么存在、各部分怎样协作；不能用职责表格取代解释。
3. 对每项精选原则，读取 [design-principle-template.md](design-principle-template.md)，先完成其中的内部因果简表，写完这一项后再继续下一章节。任何必填槽位缺少证据的原则都不能进入教科书。
4. 让模块清单服从设计主线。简单模块只使用带源码链接的精简正文。只有模块包含值得学习的非显然机制时，才读取 [complex-module-template.md](complex-module-template.md)。
5. 必要时在设计原则末尾加入简短、由源码支撑的启示：说明它解决的更普遍问题、这项设计值得采用的条件，以及何时简单方案更合适。把内容留在当前原则内，写完这三点就结束。

除非用户要求改变受众，否则面向不同经验程度和编程语言背景的程序员写作，但不要声明受众画像。术语在第一次真正需要它的句子或段落中解释，不能单独建立词汇表。先用不依赖具体实现语言的方式介绍概念，再说明仓库如何通过实际语言和框架表达它。把调用链、状态变化、测试和失败场景编入相关设计讨论，不能单独建立证明章节。只有用户要求时才添加源码阅读说明、学习顺序或练习。

使用读者能从最终文档直接打开的 Markdown 链接。保存后检查相对路径，并在正文中写出文件名和符号名，使讲解在行号变化后仍然可用。
